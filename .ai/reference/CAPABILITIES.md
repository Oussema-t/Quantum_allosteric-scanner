# Capability Catalog

This file tracks reusable capabilities independently of the provider that implements them.

Capabilities should be slash-command-friendly when they are likely to become user-facing entry points.
That means small explicit inputs, bounded scope, predictable output, and no hidden script assumptions.

Provider order:

1. MCP or tool server
2. repo-local script or wrapper
3. manual fallback

In heavily manual customer environments, repo-local wrappers that produce local artifacts or read-only output are usually the first safe automation step before any backend-integrated provider.

| `doc.submission.build` | One command: render the Phase-1 submission HTML twin to a **numbered PDF** and certify it as a side effect — page budget (6pp body / 3pp appendix), A4, ≥10pt font, no clipped/overflowing tables — plus a change report vs a git ref | `.ai/tools/submission_build.py [--html PATH] [--since GITREF] [--version N] [--json]` | repo-local; **macOS-local by design** (needs Google Chrome); dev-only `pdfplumber` dependency (not in `requirements.txt`, same policy as `pytest`) | write (scoped): only `__WORK_IN_PROGRESS__/documentation/_build/` (gitignored) | TASK-0341, hardened by TASK-0342. **Renderer:** headless Google Chrome `--headless=old --print-to-pdf` on the CI-parity-enforced HTML twin (`--headless=new` deadlocks against a running Chrome on macOS — found live) — no `pandoc`/`weasyprint`/`wkhtmltopdf`/`chromium` needed, no third Markdown→PDF artifact. A `no horizontal overflow` check catches content that, once allowed to reflow, spills past the page margin — disclosed as unable to see content some other overflow:hidden/auto box clips to nothing, since that leaves no trace in the PDF; render-and-eyeball once per structural change is the documented fallback. **Change report** reuses `doc_parity.py`'s own extractors (numbers/headings/identifiers) against `--since` (default `HEAD`) → figures added/removed, headings added/removed/reordered, per-section word delta, appendix-split moves. Version is `max(existing v<N>)+1`; PDF + `.report.txt` are named `PHASE1_SUBMISSION_v<N>_<sha>[-dirty]` so an uploaded artifact traces back to a repo state. Exit 0 PASS / 1 compliance FAIL / 2 usage / 3 environment. Ships with `test_submission_build.py`: pure-function tests (no Chrome) prove the page-budget gate FAILS on a seeded over-length doc, the clipping check FAILS on a seeded margin overflow, the appendix-split detector is NOT fooled by an inline "(Appendix C)" mention, and the change report DETECTS a seeded number change ([[TASK-0319]] bar); Chrome e2e tests skip (not fail) when a sandbox blocks the render. |

Does **not** replace the HTML route — both coexist; which one the submission actually ships from is an owner/Reviewer decision, not made by this capability. Ships with `test_submission_build_latex.py`: 19 pure-function tests + 3 end-to-end (skip, not fail, when pandoc/tectonic/pdfplumber are absent or a compile hits a network/timeout issue) — including the [[TASK-0319]] acceptance bar (seeded over-length document FAILs) and a precise determinism boundary check. |

**Invoke it directly — don't pipe or redirect its output** (e.g.

practice — `status` with no args prints one short line per active claim
(9 lines total as of this writing), and single-task `status TASK-ID` is
one line. Matches TASK-0025's broader command-hygiene guidance: prefer a
single, non-piped command over an ad hoc shell pipeline.
