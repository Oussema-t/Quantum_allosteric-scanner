- Source: direct incident, this session, 2026-07-04 ~18:1x — a Skills
  Crafter thread needed to split `.ai/COMMON.md`'s registry-row additions
  from a concurrent Toolsmith thread's claim-mechanism rewrite into separate
  commits. It did so via `git checkout HEAD -- .ai/COMMON.md` (reset both
  index and working tree to HEAD) → edit → commit → restore-from-backup —

  guarantee, not a lucky manual intervention.
- Scope: `claim`/`release`/`status` already exist and work correctly for
  `TASK-XXXX[.NNN]` ids; this subtask only widens what counts as a valid
  claim target. `sync` is unaffected — it only ever writes task-row claim
  cells, never whole-file locks.

## Intent Contract

- Outcome: before any thread runs a risky whole-file operation on a shared
  coordination file (`git checkout -- <path>`, a multi-step edit spanning
  several tool calls, a manual restore-from-backup, etc.), it can run
  `claim.py claim <resource> "<label>"` using the file's own name/path as
  the resource id — not just a `TASK-XXXX` id — so another thread checking
  `claim.py status` sees "hands off" before duplicating the mistake this
  task is filed against.
- In Scope:
  - `normalize_task_id` currently requires a digit via `TASK_ID_RE` and
    raises `SystemExit` on anything without one (e.g. `"COMMON.md"` fails
    today) — widen this so a non-numeric argument is accepted as a literal
    resource id instead of erroring, sanitized for use as a filename under
    `.ai/tasks/.locks/` (e.g. `COMMON.md` → `.ai/tasks/.locks/COMMON.md.lock`
    or a clearly-namespaced variant so it can never collide with a real
    `TASK-XXXX.lock`).
  - `claim`/`release`/`status` all work unchanged for these resource ids —
    same `O_EXCL` atomicity, same `--force --reason` override path.
  - `sync` explicitly ignores resource-id locks — it only ever reads/writes
    `TASK-XXXX` row cells in `.ai/COMMON.md`; a resource-id lock has no
    registry row and must not produce a "no task file on disk" warning
    (that warning stays scoped to actual `TASK-XXXX` ids).
  - document the convention in `.ai/tasks/.locks/README.md` and add one line
    to `.ai/COMMON.md`'s Current Rules: before any working-tree-level
    operation on `COMMON.md` itself (not a normal row edit), claim
    `COMMON.md` as a resource first.
- Out Of Scope:
  - generalizing this into a full distributed-lock system for arbitrary
    repo files — scope stays this one motivating case (`COMMON.md`) plus
    the mechanism being generic enough to reuse if a second shared-file
    hazard shows up; don't pre-build a lock registry for files nobody has
    hit a race on yet.
  - changing how `sync` regenerates task-row claims — untouched.
- Constraints And Invariants:
  - still advisory, not an OS-level file lock — matches every other claim
    in this scaffold's philosophy (a reader/thread has to check `status`
    for it to help; nothing prevents ignoring it).
  - Python stdlib only, no new dependency.
- Planned Validation: `claim.py claim COMMON.md "test"`, confirm
  `.ai/tasks/.locks/COMMON.md.lock` (or equivalent) is created and doesn't
  collide with or get misread as a `TASK-XXXX` lock by `status`/`sync`;
  confirm `sync --check` still exits clean with an unrelated resource lock
  present (i.e. it's correctly ignored).

### State found

`normalize_task_id` already had the `RESOURCE-` prefix, `_RESOURCE_
SANITIZE_RE`, and the digit-free -> resource-id path (the Open Question's
recommended namespacing, resolved). `is_task_id()` already returns false
for `RESOURCE-*` and `GIT-COMMIT`. `cmd_status`'s dangling-lock check
(`is_task_id`-guarded), `move`/`resolve`'s task-id-only refusals, and
`check-staleness`'s graceful "no snapshot for a non-path arg" were all in
place. `TestResourceIdSupport` (5 tests) existed.

### Footgun found and fixed

The id-vs-resource split was `TASK_ID_RE.search(raw)` with `TASK_ID_RE =
r"(\d+)(?:\.(\d+))?"` -- a digit *anywhere* in the argument. So a real
filename with a digit in it silently resolved to a task id:
`PHASE1_SUBMISSION_V3.md` -> `TASK-0001`, `file_with_digit_2.md` ->
`TASK-0002` (verified live before the fix). In a coordination-*safety*
tool that is a genuine hazard -- you think you locked your file, you
actually locked (or `--force`-override) `TASK-0001`.

**Fix**: `TASK_ID_RE` is now anchored to the whole stripped string --
`^(?:TASK-)?(\d+)(?:\.(\d+))?$` (case-insensitive prefix), applied with
`.match`. The argument takes the task-id path only if the *entire* string
is a clean task-id shape; everything else -- including a digit-bearing
filename -- falls through to the resource-id path.

**Blast-radius analysis** (this is a classification change in a function
every subcommand calls, so it was checked, not assumed):
- Every documented task-id form still resolves identically: `24`,
  `TASK-0024`, `TASK-24`, `26.1`, `TASK-0026.001`, `9001`, `task-9001`,
  `9001.2` -- all verified, plus a new regression test
  (`test_bare_and_prefixed_forms_resolve_to_the_same_task_id`,
  `test_dotted_subtask_shape_still_resolves`).
- The only inputs whose classification changes are strings that are
  *neither* a clean task id *nor* were ever a sensible task reference
  (`PHASE1_SUBMISSION_V3.md`, `TASK-0024 (the retry)`, `see 24`). Those
  previously mapped to whatever number appeared first; they now become
  `RESOURCE-*` ids. Could not construct a real workflow that passes a
  messy digit-containing string *intending* a task id and relies on
  `.search` extracting it -- `claim.py` is called programmatically under
  a strict convention and its own docstring only ever documented clean
  forms.
- Full `.ai/tools/` suite: **160 passed** (156 before, +4 new), zero
  regressions -- including the pre-existing
  `test_argument_containing_a_digit_still_resolves_as_a_task_id` (bare
  `9001`), which still passes.
