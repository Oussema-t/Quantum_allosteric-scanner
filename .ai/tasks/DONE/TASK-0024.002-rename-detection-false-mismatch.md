# TASK-0024.002 commit-guard/stage rename-detection false mismatch (subtask of TASK-0024)

## Context

- ID: TASK-0024.002
- Title: `claim.py`'s `_staged_paths()` (shared by `commit-guard` and
  `stage`) silently changes shape depending on git's content-similarity
  rename heuristic, making `--expect` lists for a moved+edited file
  unpredictable
- Status: Done
- Owner: Toolsmith
- Claimed By: —
- Claimed At: —
- Parent: [TASK-0024](../DONE/TASK-0024-claim-lock-tool.md) (Done) — this
  extends it rather than reopening it. Also touches
  [TASK-0028](../DONE/TASK-0028-commit-lock.md) (`commit-guard`) and
  [TASK-0029](../DONE/TASK-0029-scoped-stage-tool.md) (`stage`), both Done.
- Source: direct incident, Implementer A thread, 2026-07-09 — committing
  TASK-0009 (`claim.py move TASK-0009 DONE ...`, which renames the task
  file *and* rewrites its own `- Status:` line plus appends a large `##
  Done` section in the same change) required listing **both** the old
  `TODO/` and new `DONE/` path in `commit-guard --expect`, or the call
  failed with `staged index contains paths not in --expect`. TASK-0030,
  committed by the same thread five turns earlier via a manual `git mv`
  with a similarly large `## Done` section, needed **only the new path** —
  `commit-guard` reported "ok" without the old `TODO/` path listed at all.
  Root-caused empirically (isolated scratch git repo, not guessed): `git
  diff --cached --name-only` (no `-M`/`--no-renames` flag, so it uses
  git's default rename-detection threshold, config `diff.renames` unset in
  this repo) collapses a moved file to one path only when the old/new
  content stays above git's similarity threshold; once the edit is large
  enough relative to the file's size, git reports it as a plain
  delete+add and both paths appear. TASK-0030's edit happened to land
  above the threshold; TASK-0009's (proportionally larger, plus the
  `move` subcommand's own extra Status-line rewrite) landed below it. Nothing
  about `--expect` lists changed between the two calls — only file-content
  proportions did.
- Scope: `_staged_paths()` in `.ai/tools/claim.py` (the function shared by
  `commit-guard` and `stage`'s self-verification, per that function's own
  docstring: "Shared by commit-guard and stage's self-verification step so
  the two never drift out of sync with each other" -- they don't drift
  from each other, but both drift against caller expectations the same
  way). No change needed to `move`, `claim`, `release`, or `sync`.

## Intent Contract

- Outcome: whether a moved-and-edited file's old path must appear in
  `--expect` is a fixed, documented rule -- not something that depends on
  how much text happened to change in that particular edit. A caller
  should be able to predict the exact `--expect` list from "did I rename
  something" alone, not from re-running the command, seeing it fail, and
  reading the error to discover which paths git happened to pair.
- In Scope:
  - reproduce the two behaviors in an isolated scratch git repo (see
    Evidence below for the exact commands) as a regression check before
    changing anything.
  - fix `_staged_paths()` to use `git diff --cached --name-only
    --no-renames` -- confirmed in the reproduction (see Evidence) to
    deterministically report **both** the old and new path for every
    rename, regardless of content-similarity, removing the
    threshold-dependent branching entirely.
  - update `commit-guard`'s and `stage`'s error/help text and
    `.ai/reference/CAPABILITIES.md`'s `repo.commit.guard`/`repo.commit.stage`
    rows to state the resulting rule explicitly: "a renamed path always
    counts as two entries (old path removed, new path added) -- list both
    in `--expect`, never just the new path."
  - re-run TASK-0009's and TASK-0030's actual commit `--expect` lists
    (both cited above) against the fixed tool as a regression check: both
    should now behave like TASK-0009's did (old+new required) --
    TASK-0030's old commit is not being re-created, this is just
    confirming the new deterministic rule would have applied to it too.
- Out Of Scope:
  - changing `claim.py move`'s own mechanics (still `os.rename` + `git
    add`, not `git mv` -- this task doesn't require switching to `git mv`,
    since `--no-renames` makes the distinction irrelevant to the
    comparison either way).
  - a general rename-aware mode (e.g. an opt-in `--allow-renames` flag
    that lets a caller pass only the new path) -- not requested, adds a
    second code path for a case nobody has asked for; always-split is
    simpler and sufficient.
- Constraints And Invariants:
  - Python stdlib only, no new dependency (matches TASK-0024's own
    constraint).
  - must not change `sync`'s behavior -- it doesn't call `_staged_paths()`.
- Planned Validation: the scratch-repo reproduction below, before and
  after the `--no-renames` change; then a real `commit-guard --expect`
  call in this repo against a manufactured small rename+small-edit (like
  TASK-0030's case) to confirm it now also requires the old path, where it
  previously did not.

## Evidence (reproduction, 2026-07-09)

In an isolated scratch git repo (not this one):
1. `git mv a.md b.md` (no content change) -> `git diff --cached --name-only`
   prints only `b.md`.
2. Same rename, then edit `b.md` so more than half its lines are new
   content, `git add b.md` -> `git diff --cached --name-only` prints both
   `a.md` and `b.md`.
3. Repeating step 1's *trivial* rename but diffing with `--no-renames`
   added -> prints both `a.md` and `b.md` too -- i.e. `--no-renames`
   collapses the two behaviors above into one, always.

## Done — 2026-09-09, Toolsmith

### Reproduced first, exactly as the task's own Evidence section specifies

Scratch repo (not this one), git's default rename detection:
- Trivial rename (`git mv a.md b.md`, no content change): `git diff --cached
  --name-only` → `b.md` only.
- Same rename, then edit `b.md` so most of its lines are new content: →
  `a.md` and `b.md` both.
- Either case with `--no-renames` added: → `a.md` and `b.md` both, always.

Matches the task's 2026-07-09 findings exactly, on today's git — the bug
was still live and unfixed (`_staged_paths()` had no `--no-renames`,
confirmed by reading the code before touching it).

### Fix

`_staged_paths()` in `.ai/tools/claim.py` now runs `git diff --cached
--name-only --no-renames`. This is the only functional change — both
`commit-guard` and `stage` call it unchanged, so the fix applies to both
without touching their own logic (matches the task's own scope note: no
change needed to `move`/`claim`/`release`/`sync`, none of which call this
function).

### Documentation updated per the task's own In-Scope list

- `commit-guard --expect`'s and `stage --expect`'s `argparse` help text now
  state the rule directly: a renamed path always counts as two entries.
- `.ai/reference/CAPABILITIES.md`'s `repo.commit.guard` and `repo.commit.stage`
  rows updated with the same rule and the reproduction evidence.
- `claim.py`'s own module docstring gets an "Extended for TASK-0024.002"
  paragraph, matching the running changelog convention every other
  extension in that docstring already follows.

### Tests — `test_claim.py`, `TestRenameAlwaysSplitsIntoTwoPaths`

Three new tests, all via the existing scratch-repo/subprocess harness
(`_make_scratch_repo`/`_claim`), not synthetic unit calls on
`_staged_paths()` directly — the bug is about what real `git mv`/`move`
sequences produce, so the regression check exercises the real CLI path:

1. **Small-edit rename** (`move ... IN_PROGRESS` on the scratch task's short
   file — a plain Status-line rewrite, nothing else): `commit-guard --expect`
   with only the new path now **fails**, naming the old path as unexpectedly
   staged. Before the fix this was the surprising case — it used to *pass*
   with only the new path, because the edit was small enough to stay above
   git's similarity threshold.
2. **Large-edit rename** (`move ... DONE` after padding the file with 50
   extra lines, simulating a real `## Done` section): same assertion,
   confirming the case that already worked correctly before the fix still
   does — the fix closes the gap rather than moving which case is
   surprising.
3. **`stage`'s own self-verification**, not just `commit-guard` called
   directly — same rule, same failure mode, via the shared
   `_staged_paths()`/`_compare_staged()`.

### A real regression found and fixed in the same pass — not hypothetical

Running the full existing `test_claim.py` suite after the fix (before
adding any new tests) surfaced a genuine failure:
`TestStageRestagesEditedContent::test_stage_picks_up_an_edit_made_after_an_earlier_stage`
(TASK-0223's own regression test) started failing. Root cause: that test's
`move ... IN_PROGRESS` on the scratch task's short file is exactly the
"small edit" case above — it was written when that case collapsed to one
path, and passed `--expect` with only the new path. Fixed by adding the old
path to that test's own `--expect` list; TASK-0223's actual subject (a
post-move content edit getting correctly re-staged) is unrelated and still
covered, unchanged. **This is real evidence the fix has a genuine
compatibility blast radius**, not just theoretical: any real caller
anywhere that has been passing only the new path after a *small* rename+edit
(the case that quietly worked before) needs updating now that the rule is
unconditional. None found elsewhere in this repo's own scripted usage while
making this change, but this is the kind of thing worth watching for.

Full suite after the fix: `python3 -m pytest .ai/tools/` → **126 passed**
(all of `test_claim.py`, `test_doc_parity.py`, `test_submission_build.py`,
`test_submission_build_latex.py`, `test_task_reconcile.py` together) — no
other regression.

### Planned Validation — satisfied via the scratch-repo tests, not a manual real-repo rename

The task's own Planned Validation asked for "a real `commit-guard --expect`

path with less risk of leaving stray staged state behind.
