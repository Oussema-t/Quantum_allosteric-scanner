## The claim
Allosteric sites are **effector-specific**: one protein has different
allosteric sites for different effectors. Our answer key uses **one**
ground-truth pocket per target — the drug-bound one.

If ASD [25] lists additional annotated allosteric sites for our targets, then
residues scoring high at those sites are being counted as **false positives
when they are genuine allosteric sites**. Our reported false-positive rate
would be overstated, and every AUC computed against a single-site key is
measuring against an incomplete answer.

**Mechanistic link to HYP-P13** (`physics.md`, not yet run — a hypothesis
this task's own result bears on, not a premise this task depends on): ref
[6]'s effector-specificity claim is normally read as a database-completeness
question (ASD might just list more sites). HYP-P13 gives it a *mechanistic*
reading instead — if allostery is population redistribution across a
conformational ensemble rather than propagation to one fixed site, different
effectors plausibly select/stabilise *different* substates, each with its
own accessible pocket, by construction — not because the database happens to
annotate more sites, but because the underlying physics predicts more than
one is real. This task's own result (does ASD list additional sites, and
does re-scoring against the union key change the false-positive rate)
is therefore also indirect evidence on HYP-P13's own plausibility, even
though this task can be run and reported on its own terms regardless of
HYP-P13's status. Do not conflate the two: a positive result here
(ASD lists more sites) supports both ref [6] alone and HYP-P13; a null
result (ASD lists nothing extra) narrows ref [6]'s own claim but does not
by itself falsify HYP-P13, which predicts multiplicity via ensemble
population, not necessarily via existing ASD annotations.

**Environment finding, load-bearing for anyone re-running this**: ASD's
own HTTPS endpoint (`mdl.shsmu.edu.cn/ASD`) has an **expired TLS
certificate** — `WebFetch` fails outright ("certificate has expired"),
with no HTTP fallback (it force-upgrades to HTTPS). Worked around with
`curl -k` (skip cert verification — acceptable for reading public
scientific data, not for anything credential-bearing). The site's own
AJAX API (a legacy Ext.js/JBoss app) needs POST not GET (a bare GET 500s
with a `NullPointerException`), and its JSON has an unquoted `data:` key
(valid JS, invalid strict JSON — needs a one-line regex fix before
`json.loads`). `BrowseSite` (the sites table) ignores its own pagination/
filter params entirely and always returns the full table (3102 rows) —
client-side filtering by the protein's own `db_serial` prefix is what
actually works, not a server-side query param. All of this reproduced
in `__WORK_IN_PROGRESS__/scripts/task0229_003_asd_multisite_audit.py`,
not just asserted — running it re-derives every number below live.

**The apparent "2 domains" for BCR_ABL1 is not 2 sites** — checked
directly (every record's own `organism` field), domain `_1`/`_2` is a
**human-vs-mouse ortholog split** (ASD's own structural-domain bookkeeping,
not a site-cluster label): `_1` = human ABL1 structures, `_2` = mouse Abl1
structures of the *same* myristoyl-pocket chemistry (asciminib/ABL001
analogs appear in both). **The real second site is a different
record inside domain `_1` itself**: PDB `5DC4`, ref "Allosteric
Inhibition of Bcr-Abl Kinase by High Affinity Monobody Inhibitors
Directed to the Src Homology 2 (SH2)-Kinase Interface" (PubMed
26912659) — a monobody bound at a location the paper's own title already
names as structurally distinct from the myristoyl pocket.

**Verified, not taken on the paper's title alone**: fetched `5DC4` live
(`backend.data_layer.fetch`), computed real heavy-atom contact residues
between ABL1 (chain A, resolved 140–239) and the monobody (chain B,
resolved 4–95) at 4.5 Å (this project's own established pocket-contact
cutoff) — **24 residues, 143–239** (full list in the JSON artifact).
Confirmed disjoint from every existing BCR_ABL1 label this project uses:
zero overlap with `backend/systems.py`'s `active_site` (248–363), zero
overlap with the incumbent myristoyl `pocket_full` at 4.5 Å (356–525),
and zero overlap with this project's own currently-saved top-5 reported
hit list for BCR_ABL1 (`results/BCR_ABL1/hit_list.json`: residues 402,
311, 310, 301, 338 — none in 143–239).

**Consequence for the false-positive rate, stated precisely**: for the
specific, already-published top-5 hit list checked, **zero correction** —
none of our own reported hits fall inside the newly-found second site, so
nothing already reported changes. This does **not** fully close the
question the way a whole-protein re-score against the union key would:
only the top-5 cut was checked (the artifact actually saved for this
target), not the complete per-residue ranked array, so a residue scoring
moderately (outside the top-5 but still flagged in some other analysis)
inside 143–239 would still be silently misclassified as a false positive
today. Flagged as the honest remaining gap, not silently closed — a
full re-score needs the whole-protein score array, which was not saved
for this run and would need a pipeline re-run to reproduce, outside this
task's own "cheap, database lookup" scope.

**HYP-P13 cross-reference** (this task's own Context section, added on
