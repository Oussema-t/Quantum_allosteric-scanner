### Run mechanics

`.004`'s orchestrator (`__WORK_IN_PROGRESS__/scripts/run_challenge.py`)
run for real: `../.venv/bin/python3 -u scripts/run_challenge.py --target
KRAS_G12C BCR_ABL1 CARDIAC_MYOSIN`. Live RCSB fetches, real
`frozen_context`-gated selection/scoring, real `stamp_provenance`. Output
written to `__WORK_IN_PROGRESS__/results/<target>/` (`connectivity_matrix.npz`,
`hit_list.json`, `report.txt`, `verdict.json`) — permanent files on disk,
not ephemeral.

**Note on apparent "stalling":** the orchestrator collects all targets'
results before printing anything (`[run_target(name, ...) for name in
args.target]`, summary printed only after the whole list comprehension
returns) and was invoked through `| tail -150`, which block-buffers
Python's stdout — so long silences during a multi-target run are
expected, not evidence of a hang. Per-target output files land on disk
as soon as that target's own `run_target` call returns, independent of
when the summary prints — `find results -type f` is the reliable way to
check real progress. For live progress, run one target at a time with
`python3 -u` (unbuffered) and no pipe.

### Finding 1 — KRAS_G12C: AUC 0.779, but this contradicts a previously-documented, tested result for the same target

`AUC_apo_Hnew_default = AUC_apo_Hnew_optimised = AUC_ctqw_mean = 0.779`,
`_diagnosis: NO_FAILURE_DETECTED` (cleared both the chance check and the
`degree_centrality` floor — `floor_scores` was wired for real via
`.004`'s script, not left `None`). Cross-checked the top-5 hit-list
resnums (34, 35, 36, 11, 59) against `backend/systems.py`'s independently
-sourced `pocket_full[4.5]` reference (`test_labels.py`'s pinned KRAS
regression, 21 residues: `{9,10,11,12,13,16,34,58,59,60,61,62,63,68,69,
72,95,96,99,100,103}`) — **3 of 5 land directly in it** (34, 11, 59), a
real enrichment against a ~12% baseline prevalence, and impossible as a
trivial self-hit since `exclude_idx` already masks out `active_site`
residues before ranking.

**This is a genuine discrepancy, not a clean win to report at face
value.** `test_analysis.py::test_kras_g12c_real_target_near_chance_and_
flat_dephasing` already asserts `0.3 < AUC_apo_Hnew_default < 0.7` for
this exact target ("near chance even with the answer key") — 0.779 falls
outside that band entirely. Three real methodology differences between
that test and this run were identified (not yet isolated — that's
[[TASK-0093]]'s job):

1. **Cutoff**: this run used 8.0 Å (`targets.yaml`'s `enm_cutoff`); the
   old test used 10.0 Å (its own default).
2. **Pocket-label definition**: this run scores against `build_labels`'s
   assembled `.pocket` (`pocket_raw & ~active_site & ~terminal`,
   TASK-0070, which post-dates the old test); the old test scored
   against the *raw* `holo_pocket_mask` output, pre-exclusion.
3. **Propagation source**: this run seeds from `active_site` computed
   directly on apo (`build_labels` → `functional_indices(apo.coords,
   ...)`); the old test seeded from a holo-computed functional set
   cross-mapped to apo via `align_apo_holo`.

**Explicit instruction to whoever reviews or picks up [[TASK-0093]]:
neither number should be treated as "the" KRAS_G12C result until this is
resolved.** The 0.779 number is not dismissed as noise (it survived the
floor check and an independent reference-set cross-check) and the 0.51-
0.53 number is not dismissed either (it is a real, previously-verified,
asserted regression test on the same live data). This is a genuine
methodology-sensitivity finding worth understanding in its own right,
independent of which number eventually gets reported.

### Finding 2 — BCR_ABL1: AUC 0.525 (chance), correctly flagged `NO_SIGNAL_IN_APO` — but classical heat kernel on the *same operator* scores 0.731

Full headline block:

| Quantity | Value |
|---|---|
| `AUC_apo_Hnew_default` (CTQW, H_new) | 0.525 |
| `AUC_apo_H10_baseline` (CTQW, H10) | 0.558 |
| `AUC_ctqw_mean` (H_new, CTQW) | 0.525 |
| `AUC_heat_mean` (H_new, classical heat, **same operator**) | **0.731** |
| `_diagnosis` | `NO_SIGNAL_IN_APO` |

This is the honesty pipeline (TASK-0058/0071) working correctly on a
real target for the first time — a near-chance result gets called out,
not dressed up as a pass.

**Two axes must not be conflated when reading this** (a mistake the
report's own line-1/line-2 wording invites if read carelessly):

1. **Operator choice** (H_new vs H10), both CTQW-propagated: gap is
   `-0.033`, correctly called "noise-level" by the report itself. Not
   interesting.
2. **Propagator choice on the same H_new operator** (CTQW vs heat): gap
   is `-0.206` — large, and what `_diagnosis` is actually about.
   `_diagnosis` is computed **only from `qvc["ctqw"]["occ"]`**
   (`run_frozen_verdict`'s own code: `classify_failure(qvc["ctqw"]["occ"],
   ...)`), never heat's — so `NO_SIGNAL_IN_APO` is a statement about CTQW
   specifically, not about BCR_ABL1 as a target. A precise summary:
   *"On BCR_ABL1's optimized apo operator, classical heat diffusion
   produces a real, floor-beating signal (AUC=0.731) while the coherent
   quantum walk does not (AUC=0.525) — the honesty pipeline's diagnosis,
   which evaluates CTQW specifically, correctly flags this."*

**Why this is not already explained by this repo's existing "coherence
adds ~nothing" finding, and must not be treated as redundant with it:**
`test_kras_g12c_dephasing_flat_survives_kappa_calibration` found KRAS's
AUC is flat across a *calibrated* Haken-Strobl dephasing sweep (CTQW vs.
progressively dephased CTQW, `gamma: 0 -> large`). BCR_ABL1's gap here is
CTQW vs. `propagators.heat` — a different classical diffusion process
(`exp(-Ht)`), not proven equivalent anywhere in this codebase to the
`gamma -> large` limit of Haken-Strobl dephasing. **KRAS's flat-sweep
result does not predict what a calibrated dephasing sweep would show for
BCR_ABL1.** This is an open, target- and propagator-specific question,
directly testable with already-built machinery (`analysis.dephasing_sweep`
+ `superpose.calibrate_kappa`/`mode_energetics`, the exact recipe the
KRAS test already established) — [[TASK-0091]] runs it. If AUC rises
toward ~0.731 as `gamma` increases and plateaus, that is a genuine ENAQT
finding (PLAN.md's own "calibrated dephasing reopens blocked paths"
hypothesis, `HOLO_DIRECTION_MODULE.md` Step 4) worth pursuing further; if
it stays flat, coherence isn't the lever for this target either and the
KRAS pattern generalizes.

### Finding 3 — apo-only scoring is a diagnostic limitation, not a design flaw, and TASK-0067's own prior finding tells us how to read it

`.004`'s orchestrator deliberately does not wire holo-side numbers (its
own docstring: "real, untested scope of its own"). The user asked
whether holo should be compared, given holo is "where the actual signal
propagation takes place" biologically. **The correct framing, which must
survive into whoever picks up [[TASK-0092]]:** holo can never legitimately
*replace* the apo prediction (a real predictive setting never has holo in
advance — this is `PLAN.md`'s own "is the answer even in the apo
topology?" framing) — but computing it is still valuable as a
**diagnostic upper bound**, because it distinguishes two different
explanations for a poor apo result: apo genuinely lacks the information
(a real cryptic-pocket finding) vs. the propagator/operator itself is the
bottleneck (holo wouldn't have helped either). [[TASK-0067]] already ran
exactly this comparison once, for the bare GNM-Kirchhoff operator family
(no potential terms, heat-kernel scoring): the apo/holo gap was tiny
(KRAS +0.009, BCR_ABL1 -0.020), an order of magnitude smaller than the
cutoff/weight-scheme spread being measured there. **That finding has not
been checked for the full `H_new` pipeline** (potential terms, CTQW, the
actual winning-candidate selection this real run uses) — [[TASK-0092]] is
that check, reusing TASK-0067's own `_holo_native_labels` construction
rather than re-deriving it.
