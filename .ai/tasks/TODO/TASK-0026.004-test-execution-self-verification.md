## Intent Contract

- Outcome: a thread that just changed `backend/` or `frontend/` code can
  run one whitelisted command — no ad hoc flag reconstruction, no
  permission prompt — and get a real pass/fail answer about whether its
  change works, for exactly the slice it touched (API only, one UI tier,
  or the full suite). This is the mechanical backbone the repo's built-in
  `/verify` skill should be able to call into for Product changes
  specifically (as distinct from `__WORK_IN_PROGRESS__` research-code
  verification, which has its own existing `pytest`-based test tree).
- In Scope:
  - once TASK-0021/TASK-0022 land (or incrementally, as their test
    directories start to exist), define named request-file presets — e.g.
    `.ai/tasks/playwright-local-run.request.json` variants or a small set
    of named presets (`api-full`, `ui-tier1`, `ui-tier2`, `ui-tier3`,
    `ui-tier4`, `all`) — mapping each to the concrete
    `npx playwright test <path>` invocation `repo.test.playwright-local`
    should run. Presets are the allowlist surface: a thread picks a preset
    name, it does not compose its own Playwright CLI flags.
  - add `repo.test.pytest-local` as a sibling capability in
    `.ai/reference/CAPABILITIES.md` (same wrapper shape as
    `repo.test.playwright-local`: pinned working directory/env, named
    presets, `--json` summary output) for whatever pytest-based
    Python-level test layer exists or is added later (e.g. a future
    `backend/*.py` unit-test task, or the existing
    `__WORK_IN_PROGRESS__/tests/` suite) — do not build Python test
    *content* here, only the whitelisted execution wrapper.
  - draft (not apply) the `.claude/settings.json` allowlist entries for
    both capabilities' preset invocations, for human approval — same
    approval-gated pattern TASK-0025/TASK-0026.003 already use.
  - a short note in `SOFTWARE.md` §9 (or wherever TASK-0021/0022 end up
    documenting "how to run these tests locally") pointing at the
    whitelisted wrapper as the preferred entry point over raw
    `npx playwright test`.
- Out Of Scope:
  - `repo.test.playwright-local`'s base wrapper mechanics (working
    directory pinning, env vars, request-file schema) — that is
    TASK-0026.002's contract; this subtask consumes it, doesn't rebuild it.
  - writing the actual test content — TASK-0021 (API), TASK-0022 (UI).
  - a Python unit-test *suite* for `backend/*.py` — out of scope until such
    a task exists; this subtask only makes sure the execution wrapper is
    ready for it, per the user's tool-split instruction, not that it
    pre-builds tests for a layer nobody has scoped yet (YAGNI).
  - scaffold-coordination command hygiene (TASK-0025) — that's `.ai/`
    process commands; this is Product test execution, a different
    audience explicitly per TASK-0025's own scope note.
- Constraints And Invariants:
  - Python stdlib or POSIX shell only for the wrapper itself, matching
    TASK-0026's blanket constraint — the *tests* it runs may use
    Playwright/pytest as runtime dependencies (dev-only, not shipped to
    Render), but the wrapper script invoking them stays dependency-free.
  - preset names, not free-form flags, are what gets whitelisted — this is
    the actual safety property of "whitelisted": a thread can pick
    `ui-tier1` but can't smuggle arbitrary shell through the capability
    call.
  - must not run tests against production (Render) — presets always point
    at a locally-run `uvicorn backend.main:app`, never the live URL.
- Planned Validation: once at least one TASK-0021 or TASK-0022 test file
  exists, run its preset through `repo.test.playwright-local` and confirm
  the summary output matches a direct `npx playwright test` run of the
  same path; confirm an unlisted/invalid preset name is rejected with a
  clear error rather than falling through to arbitrary argument passing.
